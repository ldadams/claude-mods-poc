What are Claude Code mods?

A mod is a small plugin that changes how Claude Code itself looks and behaves. It can add a pane, a row above the prompt, a status line entry, a toast or a slash command, and it can watch, rewrite or block tool calls and prompts. Workbench is one.

Early access: the mod API moves between Claude Code releases. The type declarations that ship with your build are the authority, and this page is the map.

What a mod is

A mod is a Claude Code plugin whose hooks are functions, not shell commands. Settings hooks run a command and read its output. A mod's hooks run inside Claude Code, see each event as a typed value, and can change what happens next.

  1. An event happens. Claude calls a tool, you submit a prompt, a session starts, or the interface draws a component.
  2. Your hook gets it. Every hook has the shape ($, e, next). e is the event's input. $ is the engine interface: the UI, the session, the model, tools, files, a clock and a store.
  3. You decide. Call next(e) to carry on, next({ ...e, ... }) to change what the rest sees, or return your own answer without calling next.
  4. Claude Code continues. Other mods run beneath yours, then Claude Code's own behavior, and the result comes back up through your hook.

What you can build

Panes

A live view beside the conversation, opened with $.ui.open() and drawn by a ui.render hook. Workbench's /workbench pane is one.

A band above the prompt

A row drawn just above where you type, for what's happening right now. Return nothing and it disappears.

Status lines and toasts

$.ui.status(text) sets a status line entry and $.ui.toast(text) raises a toast, from any hook.

Rules for tool calls

A tool.call hook can deny an edit to a protected file, tidy a Bash command before it runs, or react to the result.

Prompt changes

prompt.submit rewrites what you typed, and prompt.compose adds, replaces or drops a section of the system prompt.

Commands, tools and timers

Register slash commands, give the model new tools or subagent types, run work on a timer, and read files or start processes through $.

The same mod draws in the terminal, the desktop app's Code tab, VS Code and mobile. A ui.render hook reads e.surface and gets that surface's elements, such as Box, Text and Button, from $.ui.resolve(e).

Anatomy of a mod

A mod is a folder with three files. There's no build step: Claude Code loads the TypeScript directly.

protect-env/
├── .claude-plugin/plugin.json   name, version, description
└── hooks/
    ├── hooks.json               { "modules": ["./register.ts"] }
    └── register.ts              the hooks module

A complete example

This mod stops Claude from editing .env files and shows a status line entry when a Bash command fails.

import type { Register } from 'claude-code'

const PROTECTED = /(^|\/)\.env(\.|$)/

export const register: Register = on => {
  on('tool.call', { tool: 'Edit' }, ($, e, next) =>
    PROTECTED.test(e.file_path)
      ? { deny: `${$.plugin.name}: ${e.file_path} is protected here.` }
      : next(e),
  )

  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    const ran = await next({ ...e, command: e.command.trim() })
    const failed = ran.deny === undefined && ran.isError === true
    $.ui.status(failed ? `failed: ${e.command.slice(0, 40)}` : undefined)
    return ran
  })
}

Things to know

  • It runs in its own sandbox. A hooks module has no DOM and no Node. It reaches files, processes, the network and the UI only through $.
  • State survives a reload. Values kept in $.state (this session) and $.store (across sessions) belong to Claude Code and stay. The module's own variables start over each time it loads.
  • A failing hook is skipped. Claude Code carries on without it and shows one dim line in the transcript naming the mod, the event and the reason.
  • $ stays in the file that receives it. Claude Code reads a mod's code to learn what it can do, and it follows $ only into functions in the same file. A mod split across files keeps its $ calls in the entry file and hands the other files a small adapter instead.
  • Atoms are read where they're declared. Each read or update of a session atom has to name an atom made in that same file.
  • The types come with your build. Once a mod loads, .claude-plugin/types/ holds the full API, the built-in tools' inputs and your connected MCP tools, so your editor and tsc check it.

Make and run one

  1. Ask Claude for one. Describe the pane, rule or command you want. Claude writes the mod and asks once whether to turn on hot reloading for the session.
  2. Or load a folder. claude --plugin-dir ./my-mod loads a mod for that session. Workbench is loaded this way.
  3. Edit and watch it reload. Saving a file reloads the mod. Edits Claude makes during a turn reload when the turn ends.
  4. Check it. claude plugin validate reports what the mod hooks and anything Claude Code would refuse. claude plugin test runs its *.test.ts files.
$ claude plugin validate ./protect-env
$ claude plugin test ./protect-env
$ claude --plugin-dir ./protect-env

Run with claude --debug to see every hook error and refused result in the debug log.

FAQ

How is a mod different from a settings hook or a skill?

A settings hook runs a shell command at fixed points and passes data through stdin and stdout. A skill gives Claude instructions. A mod is code that runs inside Claude Code on every event it hooks, can draw interface, and can change an event before Claude Code acts on it. A mod can still react to the settings hooks' events, as classic.Stop or classic.SessionEnd.

Do I need to write TypeScript?

No. A hooks module can be TypeScript or JavaScript, and JSX works in both. TypeScript is worth it: the declarations that ship with Claude Code narrow each event, so e.file_path is known to exist on an Edit call.

Can mods work together?

Yes. Hooks from every loaded mod form a chain, each calling next to reach the ones beneath. A mod can also add its own noun to $ and ship its types, and another mod that lists it under dependencies gets those types.

Is it safe to run someone else's mod?

Read it first. A mod can deny or rewrite tool calls, run processes and read files through $. Hot reloading only turns on when you say so, and an organization's policy or an untrusted workspace can keep it off.
